# SOMA host contract v1

## Status

This document defines the intended semantic contract for the first SOMA host interface.
It is a design contract for pre-alpha implementation work, not a claim of production compatibility.
Phase 0 implements an in-process Rust subset and has no encoded transport.
Each section distinguishes that subset from later production requirements where they differ.

## Boundary

The public module exposes three operations: `Launch`, `Execute`, and `Stop`.
The caller does not configure KVM, select a restore implementation, pass host filesystem paths, name TAP devices, or sequence clone repair.
SOMA owns those mechanisms and returns typed evidence or a typed fault.

The topology runs one `soma-vmm` process for one Machine.
The certified fastest path uses the node-local allocator from ADR 0006 to transfer one unassigned worker and sterile resource bundle before fresh Instance state is attached.
After transfer, the allocator is not on the per-Machine `Launch`, `Execute`, or `Stop` command path.

## Stable identifiers

`InstanceId` identifies one globally unique concrete Machine lifetime and must never be reused for another lifetime.
`GenerationId` is the content digest of one certified immutable Generation.
`OperationId` identifies one idempotent operation.

One `InstanceId` can have at most one live VMM owner.
The operator owns any stable resource identity that spans multiple Instance lifetimes.

## Launch

The Phase 0 `Launch` binds an `OperationId` and `InstanceId` to one `Generation` containing a `GenerationId` and exact `MachineSpec`.
Authenticated launch authority and resource leases are production requirements that are not present in the Phase 0 request.

The following list is the intended production transaction.
Phase 0 models its ordering through deterministic platform calls and does not perform the host mechanisms in the list.

1. Validate the request, authority, exact runtime compatibility, and artifact identity.
2. Establish an ownership ledger before mutating host resources.
3. Prepare private memory and disk state without modifying certified artifacts.
4. Create and restore the KVM machine.
5. Resume the guest at the certified repair point.
6. Authenticate the expected guest agent for this exact `InstanceId`.
7. Replace cloned identity, entropy, time, network, and transport state.
8. Complete the authenticated repair report for the bound Launch operation.
9. Return a Ready receipt containing the operation, Instance, Generation, the Generation's exact `MachineSpec`, and ordered milestones.

No intermediate milestone grants readiness.
Any pre-ready failure enters ordered rollback before a terminal fault is returned.
An incompatible restore never silently falls back to cold boot, another Generation, or a weaker isolation mode.

## Execute

`Execute` runs one direct non-interactive command inside a Ready Machine.
The command is executed directly rather than through an implicit shell.
The Phase 0 request bounds program bytes, argument count, aggregate argument bytes, the declared timeout value, and logical output bytes retained after the adapter returns.
It has no environment or input fields, and the Phase 0 adapter seam does not enforce elapsed time.

Phase 0 returns one terminal `Executed` value containing status and retained stdout and stderr rather than ordered output events.
The terminal outcome distinguishes a normal exit, a signal, timeout, and output-limit termination.
The current output allowance is a retained logical-result bound rather than a guest-output ingress bound.
A production adapter must bound framing and allocation before accepting guest output and must enforce the declared timeout.

## Stop

The synchronous Phase 0 interface accepts `Stop` for the matching Instance after Ready or after a Launch or Stop failure.
It cannot interleave Stop with a running Launch or Execute call.
An admitted Stop remains in Reaping while cleanup is incomplete, and replaying that exact Stop continues the same cleanup operation.
A future production event loop must support bounded interruption and prove removal of every SOMA-owned runtime resource before returning success.
Separately owned persistent data must be released but not deleted.

## Idempotency

Phase 0 compares complete in-process Rust request values structurally.
Repeating the same `OperationId` with the same Launch or Execute request replays its retained terminal result without repeating side effects.
Repeating a completed Stop request replays its terminal success without repeating cleanup.
Repeating the exact admitted Stop while it remains in Reaping continues its idempotent cleanup work.
Repeating an `OperationId` with a structurally different request returns `OperationConflict` without applying the second request.
Canonical encoding, normalization, request fingerprints, and attachment to other running operations require the future wire protocol.

When a transport exists, the caller must resolve an ambiguous outcome by replaying the exact operation rather than assuming it did not run.

## Milestones

Launch milestones are monotonic and ordered:

```text
REQUEST_ACCEPTED
ARTIFACTS_VERIFIED
MACHINE_RESTORED
GUEST_AUTHENTICATED
GENERATION_ACKNOWLEDGED
IDENTITY_REPAIRED
NETWORK_REPAIRED
FIRST_COMMAND_SUCCEEDED
READY
```

Milestones expose stable lifecycle meaning rather than backend logs or host internals.
They contain no guest output, secrets, host paths, kernel command line, or unsanitized operating-system errors.

## Faults

A Phase 0 `Failure` includes a stable kind, lifecycle phase, recovery directive, ordered completed milestones, and cleanup evidence.
Phase 0 recovery directives distinguish no retry, replace the Machine, recertify the Generation, and repair the host.
Pending Stop reaping is operation state rather than a terminal recovery directive.

Unknown security-critical enum values, malformed identifiers, invalid bounds, stale Instance identities, changed artifacts, and incompatible contracts must fail closed when their adapters exist.
Backend messages, syscall arguments, and guest-controlled strings are never copied directly into a public fault.

## Transport

The semantic contract is independent from an in-process Rust adapter or a local wire adapter.
The production local adapter will use a versioned bounded protocol over an inherited or filesystem-backed Unix socket.
Its byte encoding, framing, peer-credential policy, and compatibility digest require a separate protocol ADR before they become stable.

Tests exercise the same semantic operations as production callers.
Deterministic test adapters replace KVM, artifact, network, and guest mechanisms behind private seams rather than exposing test-only lifecycle methods.
