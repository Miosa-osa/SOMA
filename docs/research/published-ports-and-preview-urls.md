# Published ports and preview URLs

## What this document decides

A published port is now reachable.
`soma-netd` translates a host endpoint onto a guest endpoint at activation and removes the translation at release.
A reachable host endpoint is not a URL, and the distance between the two is where every remaining decision lives.

This document decides where the URL layer sits, who terminates TLS, how one URL is bound to one Instance, and which half of the problem belongs to SOMA and which half to the MIOSA platform.
It designs that layer.
It does not build it, and nothing described under "The platform half" exists.

## What SOMA does today

These are implementation facts about this repository, not targets.

The portable request carries `PortPublication` values, each naming a host bind, a host port or an automatic request, a guest port, and a transport.
Admission turns them into a `NetworkIntent` and refuses an IPv6 host bind, because the guest lease is IPv4 only in this profile.
Assignment reserves each host endpoint with one exclusive socket, and that socket is never made to listen, so a reserved but unpublished port refuses a connection instead of accepting one nothing can serve.
Assignment also renders the sandbox ruleset with the inbound rules the publication will need, which grant nothing on their own.
Activation, the same admitted step that enables forwarding, installs one `inet` table per bundle holding the destination translation at the prerouting and output hooks and a masquerade on the way out through the bundle's veth.
Release deletes that table first and the final live inspection asks for it by name, so a translation that outlived its Instance is a failed release rather than an invisible one.

The result is a host endpoint, an address and a port on one machine, live for exactly the interval between activation and release.
Everything below is about what turns that into something a person can open.

## Decision 1: SOMA's contract ends at the host endpoint

SOMA publishes an endpoint and reports it.
It does not mint URLs, hold certificates, run an HTTP proxy, or know what a tenant is.

The reasons are the ones that made the broker a broker.
A URL layer needs DNS, certificates, a public address, and an identity system, and every one of those is operator property that changes per deployment while the VMM does not.
It also needs to survive a host, because the name a user bookmarks must outlive one machine, and SOMA's units are one host's namespaces and devices.
Putting any of it inside `soma-netd` would give the most privileged process in the system a public listener and a certificate private key, which is the opposite of what a broker is for.

The consequence is that SOMA owes the layer above an exact, machine-readable answer to one question: for this Instance, which host endpoints are live, and until when.
That is what `Assigned::published` and `ActivationEvidence::published` carry today, and it is the whole interface.

## Decision 2: the URL is minted at a platform edge, and it is opaque

A preview URL has the shape `https://<label>.<preview zone>`.

The label is an opaque token with at least 128 bits of entropy, generated by the platform when a publication is activated.
It encodes nothing: not the tenant, not the Instance identifier, not the host, not the port.
A label that encoded any of those would let a reader enumerate other sandboxes by editing the name, and a preview URL is very often pasted into a chat window, an issue, or a build log.

One label addresses one published port of one Instance.
An Instance that publishes three ports gets three labels, because a single label with a port suffix would make the port guessable and would give one shared secret to three services of different sensitivity.

The zone is a dedicated domain that hosts nothing else and shares no cookie scope with the platform's own origins, so a page served out of a sandbox cannot read platform credentials or set a cookie the platform will honour.
For the same reason the zone is on the public suffix list if it is ever exposed to untrusted tenants, which is the only mechanism that stops one label writing cookies for another.

## Decision 3: TLS terminates at the edge, never on the sandbox host and never in the guest

The edge holds a wildcard certificate for the preview zone and terminates TLS there.

Terminating in the guest is unworkable and unsafe: it would need a certificate per Instance, an issuance flow on a path that must stay fast, and it would hand a publicly trusted key to the least trusted component in the system.
Terminating on the sandbox host is only slightly better; it puts key material on every host in the fleet and makes certificate rotation a fleet operation.
A wildcard at the edge is one key in one place, rotated by the team that already rotates keys.

Between the edge and the host endpoint the traffic is on the operator's own network, and it must not be trusted just because it is internal.
The requirement is mutual authentication on that hop, either mTLS between the edge and a host-side listener or a private link the host admits by identity rather than by address range.
The hop is stated here as a requirement because it is the part a reader would otherwise assume is solved.

From the edge to the guest the connection is plain HTTP over the operator network to the published endpoint.
The guest therefore never sees the TLS handshake and never sees the original client address unless the edge forwards it, which the edge does in a header the guest cannot forge because the guest never terminates the connection.

## Decision 4: the bind a preview URL uses is not the loopback default

The portable default is a loopback bind, which is the right default for a caller running on the same host as the sandbox and the wrong one for an edge on another machine.

A publication intended for a preview URL is requested with an explicit bind on the host's private address, and the operator profile decides which address that is.
The default stays loopback so that the unsafe direction requires an explicit act.
The platform is responsible for asking for the right bind, and the operator profile is responsible for refusing binds that would expose an endpoint beyond the operator network.

Requesting the IPv4 wildcard is possible and is a deliberate operator decision, not a convenience.
It publishes the endpoint on every host address including any public one, with only the edge's own reachability as a control.

## Decision 5: a label is bound to one Instance by a route record, and revocation precedes reuse

The edge resolves a label through a route record holding the Instance identifier, the assignment's cleanup generation, the host, the host endpoint, and an expiry.
The record is created when activation reports the mapping and destroyed when release reports it removed.

The property that matters is that a label must never address a different Instance after the first one is gone.
Host ports are a finite pool and are reused within minutes on a busy host, so a stale label pointing at a host and port would eventually point at a stranger's dev server.
Three rules together give the property.

The route record is keyed by label and carries the Instance identifier and generation, and the edge refuses to forward when it cannot read a live record.
The record is revoked before the port can be reused, which means the platform revokes the route first and calls Release second, and treats a revocation failure as a reason not to release rather than a detail to log.
The edge caches nothing beyond the record's own lease, so a revoked label stops resolving within one lease interval rather than at the whim of a cache.

A label that no longer resolves answers with a terminal status that says the sandbox is gone, not with a redirect and not with a generic error, because the difference is what stops a user retrying against whatever now owns the port.

Nothing here can be enforced by SOMA, which is why it is written as a requirement on the platform.
What SOMA contributes is that release proves the translation gone, and that the assignment's generation is already part of the durable record, so the platform has a value to key on that a later Instance can never reuse.

## Decision 6: a preview URL is private by default

A label is unguessable, and an unguessable label is not an authorization decision.

The edge requires the platform's own session on a preview URL by default and admits an anonymous request only when the Instance's owner has explicitly marked that publication public.
The reason is that the most common thing behind a preview URL is a development server with debug endpoints, no authentication of its own, and a database behind it.
Sharing has to be a decision someone makes, not a consequence of running `npm run dev`.

Where a publication is marked public, it is public for the life of that Instance and no longer, because the label dies with the route record.

## The SOMA half and the platform half

SOMA owns the sterile bundle, admission, the reservation, the translation, the deny-by-default rulesets, activation, release, and the proof that nothing leaked.
Its output is a list of live host endpoints bound to an Instance, and its guarantee is that the list is empty before activation and empty after release.

The platform owns the preview zone, DNS, the wildcard certificate, TLS termination, the label, the route record, revocation ordering, authentication, rate limiting, abuse handling, and the mutually authenticated hop from the edge to the host.

The seam between them is deliberately narrow: an activation reports mappings, a release proves them gone, and the platform never reaches into the broker for anything else.

## What is deliberately not decided here

Whether the edge speaks anything other than HTTP.
A raw TCP preview, a WebSocket upgrade, and an SSH endpoint each need a different addressing scheme, because a hostname label only routes what carries SNI or a Host header.

Whether a URL may survive an Instance by pointing at its successor.
That is a stable-name feature, it conflicts directly with Decision 5 as written, and it needs its own decision about what a name means.

Whether the guest may request a publication after Launch.
Every publication today is part of the admitted intent and therefore part of the intent digest that activation authenticates against, and a later publication would need a second admitted step with its own authority.

## Open questions

How the edge learns of an Instance that died without a release, given that reconciliation is the broker's answer and the edge's route record has no other source of truth.
A lease with a short expiry that the platform renews is the obvious shape, and it has not been sized.

Whether the automatic host port should come from a range the operator reserves for publications rather than from the ephemeral range, which currently makes a published port collide with outbound connections' source ports on a busy host.

What a published UDP endpoint means at the edge, where there is no equivalent of a Host header and no session to authenticate.
